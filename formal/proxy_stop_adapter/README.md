# Parallel scheduler proxy stop adapter

This model covers the translated-token path in the [adapter header](../../backport/cpp26/execution/detail/proxy_stop_adapter.hpp). It gives batch C-05 and the shared first-query case G2-06 bounded protocol evidence. `std::execution::task` uses the same adapter for a mismatched stop token ([task.state]/7), with the task's own stop source as the translated source. The model does not claim that the parallel scheduler frontend or any provider exists.

## Protocol and assumptions

- The specification is the W2 decision table accepted for pilot batch G2b, summarized in the conformance ledger at ST-07. SC compare-exchange claims first use. The winner observes once whether the upstream token can stop, unless the caller classified it statically as never stopping. If it can, the winner constructs the live source, checks that it reports a fresh stop state, issues and commits its token once and only then registers. If it cannot, the winner takes the receiver's own token when it is of the issued type (`sample`), else the in-place token's specified disengaged value (`value`), else it searches the candidates in order: the token type's nonthrowing default (`tokdef`), a source made from `nostopstate` (`nostop`) and a default constructed source (`default`). Each scenario fixes what each candidate's token reports, independently of which constructor made it: impossible, eligible (possible and not requested) or requested. The first impossible candidate is committed. An eligible `nostopstate` source is held while a default constructed one is examined in the spare slot, and is committed if nothing impossible is found (ST-07.2), as an eligible default source is. Whatever is not chosen releases its token and then its source, as two steps. If nothing is acceptable the program ends. A competitor can see ready immediately, notice it before sleeping, or park and be notified. Ready publishes the committed answer and the completed callback registration. Readers copy the committed answer, one at a time, and never call a token factory. The source skips the copy lock for `inplace_stop_token`, `never_stop_token` and `std::stop_token`, whose concurrent copies are specified to be safe; the model keeps the lock for every token.
- **Selection oracle.** `model.oracle()` computes the answer, the number of sources constructed and the number that survive from the three selection rules of the decision table alone, and `model.expected_slots()` which source survives and in which slot. `model.plan()` is the source's step sequence. Before any tier, `validate_selection()` runs one statically classified query for every combination of the three candidates (absent, impossible, eligible, requested, and a token default known to be impossible) with neither shortcut, each shortcut and both: 319 executions, since the all-absent combination is the static rejection X3 and has no execution. It compares the committed candidate, the constructions, the surviving source and its slot, and termination with its construction and factory counts, with the oracle. The 319 executions are not 319 distinct settings: with the in-place shortcut the five token-default values coincide. Representative combinations are scenarios of the interleaving model.
- **Assumptions.** A default constructed live source that is not fresh ends the program at the fresh-state check. That a fresh or eligible source is independent of every other owner for its observable lifetime is assumed and cannot be established by observation (ST-07.5). Which C++ expressions are instantiated, the static rejections and exceptions are outside the model and are covered by configure probes and death tests.
- An upstream request or callback registration can linearize first. The stop contract is the same as in the [stop-token model](../stop_token/README.md): a selected callback runs once, registration against an already requested source invokes on the registering thread, and removing an executing callback waits on a foreign invocation but not on its own thread. The model uses these abstract transitions and does not re-model the upstream source lock.
- Queries and item execution join before terminal dispatch. The terminal may race upstream stop. Outward completion may delete the proxy, so a forwarding invocation pins the source until its own call returns, independently of the proxy and registered callback. The terminal step models entry and possible immediate destruction together. The runtime trace ends at terminal cleanup and checks outward entry separately.
- The upstream can lose its last source without a request at any point of the `loss_during_initialization` scenario. The observation point is the winner's one `stop_possible()` call: a loss before it gives the impossible answer, and a loss after it leaves the issued token possible, which is the later-loss half of ST-07.2. A callback constructed after the loss is an object that is never linked for an invocation. A default constructed source that is not fresh ends the program at the fresh-state check; that the fresh state is independent of other sources is an assumption that the check cannot establish.
- The model latches an upstream request and selects the adapter's linked callback in one transition. The real upstream source selects its callbacks one at a time, so a terminal can remove the still pending forwarder while another callback of the same upstream runs, and the receiver is then entered with a latched request and no forward. That is ordinary removal of a pending callback and is outside this abstraction. The task fixture `G206_TerminalRemovesAForwardThatIsStillPending` covers it deterministically. PA1 therefore speaks of a request whose callback was selected.
- Bounds are one operation, zero to two queries, up to two upstream requests, and one outward terminal. The suite includes a request before registration (including during source setup), one racing after registration, cross-thread removal, same-thread removal from a downstream callback, a nonrequestable token in each representation, a `nostopstate` constructor that stays engaged, default sources without a state and with a requested state, a statically unstoppable token, a loss of upstream possibility before the observation, before the registration and after it, and the unused path. No C++ lowering, arbitrary custom token implementation, platform memory semantics beyond the used SC contract, backend work queues or allocator failures are proved here. Exact token and unsupported-query dispatch are covered by the C++ fixtures.

## Invariants and sensitivity

| Check | Obligation | Failing sensitivity case |
|---|---|---|
| PA1 | A stop whose forwarding callback was selected must reach the translated source | `lose_request.already_requested.2` |
| PA2 | One callback construction and one forward at most. Two sources are alive together only while a held `nostopstate` source and a default constructed one are under examination. At publication, before any reader returns: the sources ever constructed and the sources that remain are the oracle's, exactly one for a live translation, the surviving source is the one the committed answer was issued from and sits in its slot, and no candidate token is left over | `duplicate_registration.request_race.2`, `sequential_reconstruction.request_race.2`, `wrong_survivor.held_nostop_impossible_default.2` |
| PA3 | No registered callback storage at outward completion | `terminal_before_cleanup.request_race.2` |
| PA4 | A forwarding invocation may resume after destruction only with its source pin | `no_source_pin.same_thread_cleanup.2` |
| PA5 | An answer returns only after ready publication, with exactly one callback registration for a token observed possible and none otherwise, and after delivery of any stop already pending at registration | `publish_before_immediate_forward.already_requested.2` |
| PA6 | All queries, the invocation and the terminal retire | — |
| PA7 | The committed answer is the candidate the oracle selects and reports what that candidate observes. A request is never reported for an upstream that cannot stop. The program ends exactly where the oracle says no permitted answer exists, checked in both directions | `engaged_where_representable.held_nostop_impossible_default.2`, `fabricated_request.requested_default.2`, `bypassed_fresh_check.stateless_default.2` |
| PA8 | At a successful publication exactly one committed answer and one factory call per source examined. An unused adapter and an initializer that ends the program have no commit. T1 and T2 end after exactly one construction and no factory call. T3 ends after every available source candidate was constructed and had its token issued. Copies returned to readers are counted apart | `publish_before_registration.request_race.2`, `reader_issues.request_race.2`, `early_termination.requested_default.2` |
| PA9 | No two readers are inside the copy of the committed answer at once | `unserialized_copy.request_race.2` |
| PA10 | No source is released while an adapter-owned token issued from it is alive | `source_released_first.held_nostop_requested_default.2` |

The two mutants and thirteen negative controls run in both tiers. The lose-request mutant leaves synchronous invocation to the upstream library and skips `request_stop()` in the adapter forwarder. The publication controls publish too early: before the answer is committed and the callback registered (PA8), and before a committed synchronous invocation can deliver the pending stop (PA5). The PA7 controls skip a validation: one commits a held engaged `nostopstate` source without examining the default constructed one, which is impossible; one accepts an already requested default source; one skips the fresh-state check of a live source. The second PA2 control constructs the live source twice in the same cell, and the third keeps the held `nostopstate` source although the committed answer came from the default constructed one, with the right number of survivors. The termination control ends the program before a required candidate was examined. The PA8 reader control lets a reader call the token factory. The PA9 control removes the copy lock. The PA10 control releases a rejected candidate's source before its token. Each tier run validates the exact named PA category for each negative case against the [sensitivity manifest](sensitivity.txt) before the shared runner can regenerate [expected records](expected/results.tsv) or refresh the lock, and fails if the expected records name any configuration that the full tier does not select, or miss one. The passing configurations also require the scenario-specific transition coverage in [scenarios.py](scenarios.py).

## Checking and maintenance

```bash
python3 -B formal/proxy_stop_adapter/check.py --check-source
python3 -B formal/proxy_stop_adapter/check.py --tier quick --jobs 2
python3 -B formal/proxy_stop_adapter/check.py --tier full --jobs 2
python3 -B formal/proxy_stop_adapter/check.py --steps
```

Quick selects thirty-one configurations and full selects sixty-six. Each configuration is capped at 4,000 states. The tool saves results, summaries and shortest counterexamples under ignored `build/formal/proxy_stop_adapter/`. Review protocol fidelity against the C++ before refreshing [source.lock](source.lock). For changes to model or data, qualify a full run, inspect the named failures, update the expected records with `--tier full --update-expected`, then rerun separately with `--tier full --refresh-lock --assessment '<review>'`. The lock detects edits and checks function-local source anchors. It is not a proof of source/model equivalence.
