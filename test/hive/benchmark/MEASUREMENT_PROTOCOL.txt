HIVE MEASUREMENT PROVENANCE -- 2026-11-12

Scope
-----
This protocol records the R4.2 review's L8 requirement for future Hive
performance work. It supplements, rather than replaces, each approved
taskbook's workloads, fixed baselines, pairing order, sample counts, noise
rules and acceptance thresholds. Apply it to P0/P1 and related K1 tuning.
Do not retrospectively change the status of earlier batches.

Batch Identity
--------------
Each batch must retain a manifest with:
- a stable, non-private host identifier and run date;
- CPU model, architecture, core type, selected CPU, affinity and sibling
  topology; do not infer topology from CPU numbers used on another host;
- configured frequency policy, boost state, frequency limits and observed
  frequency/load during the run, plus OS/kernel version;
- memory configuration and DDR speed when available, allocator/runtime,
  compiler and standard-library versions, flags and container image identity;
- candidate, fixed baseline and previous-candidate commit IDs, source and
  binary hashes, workload/seed, timing boundary and sample/pair order.

Record unavailable metadata explicitly instead of guessing it. Keep private
machine names and local paths in ignored evidence, not committed summaries.
S7 includes allocation in its timed region; changing allocation or timing
boundaries requires a separate protocol decision, not an implicit comparison.

Same-Host Comparisons
---------------------
All implementations used for a conclusion must run on the same host, with
the same selected core and recorded environment, interleaved within the
same measurement session. Every batch also includes the previous candidate
as a named control. That control does not replace the approved fixed baseline
or external reference. For P0, preserve baseline/candidate alternating pairs
and add separately identified previous-candidate comparisons in the same
batch. For P1, include the previous candidate in the rotated implementations.
If the previous candidate is already the fixed baseline, label both roles.

On a host, CPU/core type, memory, kernel or toolchain change, start a new
measurement series. Rebuild and rerun the candidate and controls with recorded
inputs. Never combine old/new absolute timings or normalized ratios to infer
an implementation speedup, regression or acceptance result. Identical binaries
do not make different hosts comparable. Label historical results by their
original host; do not apply an old host's threshold-tuning conclusion to the
new one without new measurements.

Noise And Hardware Incidents
----------------------------
Retain every raw batch, including rejected batches, with the stated reason
and the taskbook's rerun decision. Do not select favorable samples or rerun
solely to cross a threshold. Record concurrent load and interference without
claiming exclusive use of a shared host.

If memory errors or other hardware faults are discovered, attach that caveat
to affected historical evidence. Do not treat those runs as a clean current
baseline or silently relabel them as passing, failing or harmless noise.
Claims renewed after the incident need same-environment repetitions on a
healthy host; missing repetitions remain explicit gaps. Correctness results
and timing results are separate evidence categories.

Reporting
---------
Report within-session candidate/reference ratios, paired statistics where
required, ranges and noise decisions alongside the host identifier. Keep
author P0, reviewer P1 and tuning K1 distinct; none substitutes for another.
An optional tuning target is not an admission blocker unless the approved
taskbook or owner decision makes it one.
